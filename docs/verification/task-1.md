# Task 1: measurement and performance

The distinct-user runner, stage histograms/traces, durable producer batching, atomic routing and receipt advancement, and processor concurrency changes are described in [PERFORMANCE](../PERFORMANCE.md). [Benchmarks](../benchmarks.md) link the actual source snapshots, raw ledgers, CPU samples, hardware, and before/after measurements.

Done when: the matched configured 200-user runs have complete ledgers, resource sampling, client-observed socket counts, and verified zero-lag drain. These checks passed. Independent server connection sums dipped during both runs, so uninterrupted server concurrency is not established. Peer delivery during the steady window increased from 4.87 to 11.50 messages/s. The optimized run persisted and peer-delivered all 1,367 sends; its steady-cohort p50/p95/p99 remained 37,593 / 54,907.10 / 57,673.20 ms. The 500-user ramp exposed overload and is explicitly reported as such.

Validation on the final runtime: backend formatting, lint, type checking, 76 unit tests, and build; frontend formatting, lint, type checking, nine unit tests, and build; ten Compose integration tests; eleven smoke checks. All four chaos scenarios passed across 485 sends, with zero lost messages, duplicate logical deliveries, or ordering errors; see [actual summaries](task-1-chaos/). The processor was killed at 80 persisted / 40 queued. After a stalled host-side attempt, monitoring services were temporarily stopped and the host dependency timeout was set to ten seconds for the remaining scenarios. No low-latency SLO or production capacity is claimed.
